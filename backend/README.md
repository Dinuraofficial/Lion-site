# Cloudflare + Firebase backend — staging setup

The existing website remains live; this implementation is prepared locally and is not deployed. Cloudflare Worker serves the static site and D1. Firebase Authentication signs in the officers. The Worker independently verifies signed Firebase ID tokens using Google's public keys and allows only explicitly configured UIDs. The login screen is public; private data is not. The dashboard uses short-lived tokens only in memory and requires sign-in again when a token expires. It does not currently check Firebase revocation or disabled-user status before token expiry. Remove an officer UID from ADMIN_UIDS and redeploy to revoke access immediately.

## Security and deployment prerequisites

1. The D1 database `nexus-db` and schema have been created. The database ID, Firebase project ID and initial officer UID are populated in `backend/wrangler.example.jsonc` (not secrets). Confirm this D1 belongs to the same Cloudflare account as the Worker.
2. Create a Cloudflare Turnstile widget for the deployed hostname. Supply its **site key** as TURNSTILE_SITE_KEY and its **secret** as a Worker secret named TURNSTILE_SECRET_KEY. Never commit the secret. The public form rejects submissions without valid server-side Turnstile verification. Also configure rate limits/WAF, and test spam protection before production.
3. Copy `backend/wrangler.example.jsonc` to root `wrangler.jsonc` only when ready; set the real Turnstile site key. Ensure the configuration matches existing deployment routes and asset bindings. Prefer a separate staging Worker and D1 for end-to-end testing. Git-based deployments may treat Wrangler configuration as authoritative, so verify the current Worker build/deploy settings before pushing. Use `node backend/build.mjs` as the build step and `npx wrangler deploy` to deploy the root configuration. Add `TURNSTILE_SECRET_KEY` through the Cloudflare dashboard or Wrangler secret mechanism, never in source code.
4. Test login, approved UID and unapproved users, expired tokens, write operations, content publishing, public form and spam verification, alternate hostnames, and preview deployment. Without deployed API/bindings, the current copy-and-share form remains active. Worker denies admin requests without properly verified Firebase JWT and allowlisted UID.
5. Add authorized UIDs as comma-separated ADMIN_UIDS; do not trust an email field or the keyboard shortcut as access control. Email/password accounts can be created in Firebase Authentication. Public sign-up should be disabled/restricted where possible; even a non-approved Firebase account cannot access admin APIs. Never share passwords or service-account keys. Consider Firebase MFA for officers and appropriate login abuse protections.
6. Define a privacy notice and retention/deletion policy. Inquiries are sensitive. The dashboard displays the latest 200; delete requests permanently. No email alerts, direct image uploads or photos in the dashboard are implemented; HTTPS links may be entered instead. Published entries appear in the website showcase; drafts are admin-only. D1 is not backed up by this implementation; set up backups.

Turnstile site key is public; secret is private. Firebase Web API key is public application config and not an admin credential. Restrict its use in Google Cloud as appropriate without blocking Firebase Auth, monitor quotas and don't rely on hiding the key. Worker routes `/api/*` require `run_worker_first`; it serves `build/` through the ASSETS binding. The admin overlay supports Ctrl+Shift+P where the browser allows it and an Officer Login button as fallback. Closing it clears the in-memory session by unloading the frame.
